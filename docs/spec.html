Full technical specification for a custom Android alarms / timers / stopwatch app — built because the stock one is ugly and the timer can't chain.

Five top-level panes in a bottom navigation bar. The stock app's mental model, not its execution.

04 — Alarms

Alarms

4.1 — Today's model

One-off

  • Fires once at a date + time
  • After firing: Delete or Mark as done — per-alarm toggle
  • Delete → removed immediately, no trace
  • Mark as done → stays in the list, greyed out with a "done" chip, until you toggle it back to active or delete it manually

Repeating

  • Day-of-week set (Mon–Sun)
  • "Delete after" — end date, or occurrence count
  • Email-rule style: "repeat until…" / "repeat N times"

Behavior

  • Snooze length and max-snooze count are per-alarm, not global.
  • Sound, vibration, and volume are per-alarm via the system alarm-sound picker.
  • If the alarm can't fire on time (device off, Doze denial, etc.) it fires late with a clear "this alarm was delayed" notice rather than silently skipping.

4.2 — Generalizing: scheduled triggers (design-only, not built)

An alarm is a special case of a more general primitive: a scheduled trigger — a time, a repeat pattern, and a target that fires. A zero-duration Timer is today's alarm; the same time+repeat machinery can just as well start a Timer, a Chain, or a Stopwatch. Dropping the Alarms pane in favor of "just schedule a zero-second timer" would be a worse product for purely human reasons — people think in alarms — so the pane stays, but what it can point at grows.

  • The Alarms pane gets three sub-panes: Anonymous (today's alarm, unchanged), Timer/Chain (fires by starting a persistent Timer or Chain block), Stopwatch (fires by starting a stopwatch, optionally with a name and t₀).
  • The scheduling config — time, repeat days, delete-after, snooze — is shared across all three; only the target and what "firing" means differs.
  • A repeating Timer/Chain trigger is the natural way to get "run my Workday chain every weekday at 8am" — the payoff for building this at all.
  • Snooze generalizes cleanly to "delay the trigger" regardless of target — no new concept needed.
  • Stopwatch triggers are the one wrinkle: stopwatches are deliberately in-memory-only (spec §05), but "start at T" only needs one small persisted seed (start timestamp + name + t₀) that the Stopwatch pane reads back on next open to reconstruct "this has been running since T" — it doesn't mean abandoning the in-memory design for manually-started stopwatches.
  • Scheduling a lap on an already-running stopwatch at a future time (also raised alongside this) is a separate, smaller feature — a per-stopwatch mini-scheduler, not a target type under Alarms. Tracked, not designed yet.

This is not backward-compatible with the Alarm entity as built (§03): oneOffAfterFire and done only make sense for the Anonymous target. Adopting this means splitting Alarm into generic scheduling fields (time, repeat, delete-after, snooze) plus a target sealed type, and — bigger — reworking AlarmReceiver/NotificationHelper, which are currently hard-wired to alarm dismiss/snooze semantics rather than a pluggable per-target action set. See §11.

05 — Stopwatches

Stopwatches

  • Any number of stopwatches exist concurrently, each an independent card in a list — existence isn't tied to running. A stopwatch stays in the list, running or paused, until you explicitly delete it.
  • Per card: lap (while running), pause/resume, restart (reset to t₀), delete.
  • Optional name per stopwatch.
  • Optional t₀ — a starting offset (e.g. 10:00) instead of always counting from zero. Restart resets to t₀, not to zero.
  • State model: accumulatedElapsed: Duration plus startedAt: Instant? — elapsed is accumulated when paused, or accumulated + (now − startedAt) while running. Pausing folds the running segment into accumulated and clears startedAt.
  • Kept alive only for as long as the app process is — not backed by Room, doesn't survive an app kill/reboot. Matches how you actually use a stopwatch; if that ever needs to change, it's a one-line switch to a persisted entity, not a redesign.
06 — The hard part · reworked in v0.2

Timers & chains

The core shift: a Timer or a Chain is no longer a one-shot expression that gets flattened and forgotten. Either one can be a named, persistent block that other chains reference by label — define "Work" once, reuse it everywhere, and editing it later ripples everywhere it's used. This already matches the "atom" framing from the modularity discussion: a Timer is the atom (labeled, startable, chainable), a Chain is atoms plus ordering plus per-transition metadata, and neither cares who's driving it — a person tapping Start, or (once §4.2 lands) a scheduled trigger.

6.1 — Library & config screen

The Timers pane is a library list: each card shows only label, kind (Timer/Chain), and total duration — no content or sound details cluttering the list. Tapping a card pushes a full-screen config screen onto the nav stack (not a modal or bottom sheet), the same screen shape for both Timer and Chain. A Timer's config is short (label, duration, sound, persistent) and a Chain's is long (adds transition mode, default sound, overrides, content) — deliberately one pattern for both rather than two, even though it's more screen than a bare Timer strictly needs.

6.2 — Timer (leaf block)

Configuring a Timer means setting: a duration, a label, a sound profile (tune + vibration), and whether it's persistent (off by default).

  • Creating a Timer always starts it immediately — persistent only decides whether the definition is kept afterward.
  • Not persistent: starts immediately; if you choose "stop" when it ends, it's completely gone, no trace.
  • Persistent: saved to the library and started immediately; "stop" just ends that run — the definition stays, ready to start again or be referenced by a chain.

6.3 — Chain (composite block)

Configuring a Chain means setting: a label, persistent, a default sound profile (for anonymous content), optional sound-profile overrides (per referenced block, scoped to this chain only), a transition mode, and the content itself.

Content is an ordered list where each element is one of:

  • Anonymous — a bare duration (3, 30m) with no identity of its own. Inherits the chain's default sound profile. May carry a display-only note ("lunch") that's just a label in the UI, not a reusable block.
  • A function of anonymous timers — range / arange / repeat, exactly as before, expanding to more Anonymous elements (or to a repeated group of any element, including references).
  • A reference — the label of an existing persistent Timer or Chain. Its duration and sound profile are looked up live from the source block, not copied in — so re-tuning "Work" updates every chain that references it, automatically. A reference keeps the source's own sound profile unless this chain explicitly overrides it.

Every Chain also declares its transition mode: require an interaction to advance between steps, or sound the alert and continue immediately (seamless). This is the chain's own default — it governs advancing between its steps regardless of what those steps are.

Per-step override, not per-step-by-default: rather than every step pair carrying its own transition config (real flexibility — "seamless into Break, but confirm before Work starts back up" — at the cost of configuring N−1 transitions instead of one), the recommended mechanism reuses the soundOverrides pattern that already exists for exactly this shape of problem. Extend it from Map<blockId, soundProfileId> to Map<blockId, StepOverride> where StepOverride carries an optional sound profile and an optional transition-mode override for the transition immediately following that step. Unlisted steps keep the chain's default. Not built — this is the resolution to the "does every level need its own transition metadata" question raised alongside §4.2.

6.4 — Expression grammar

chain_content  = "(" element ("," element)* ")"
element        = duration | ref | call | chain_content
ref            = IDENT                               // label of an existing persistent block, resolved live
call           = repeat_call | range_call | arange_call
repeat_call    = "repeat" "(" int_expr "," element ")"
range_call     = "range"  "(" int_expr "," int_expr ["," int_expr] ")"
arange_call    = "arange" "(" int_expr "," int_expr ["," int_expr] ")"

duration       = literal_duration | int_expr         // bare number ⇒ minutes
literal_duration = (NUMBER "h")? (NUMBER "m")? (NUMBER "s")?

int_expr       = int_term (("+" | "-") int_term)*
int_term       = NUMBER | time_func | "RANDOM" "(" int_expr "," int_expr ")" | "(" int_expr ")"
time_func      = ("MINUTE" | "HOUR" | "SECOND") "(" time_expr ")"
time_expr      = "NOW" (("+" | "-") literal_duration)?

Evaluation is still eager for durations (NOW resolves once, at start time) but lazy for references: a reference's duration and sound are read from the live source block each time it matters (display, start, total-duration calc) — that's what makes "editing Work updates every chain" true.

6.6 — Safety limits

A flat "100 links" cap stops making sense once chains legitimately run for hours across dozens of referenced steps. It's replaced by graph-shape limits instead of a raw count:

LimitDefaultConfigurable
Reference graph must be a DAGenforced, alwaysNo
Max reference depth20No
Max resolved execution-plan size300 stepsYes, hard ceiling 1000
Max multiplier per repeat/range/arange200No — use case above this isn't supported
Total durationsoft warning above 24hYes, threshold

Cycle detection is mandatory, not optional: saving a reference that would make a block contain itself — directly (Work → Work) or indirectly (Workday → Session → Workday) — is rejected at save time, with the cycle path shown in the error. Without this, total-duration can't even be computed. Plan size is still checked symbolically before expansion, the same nesting-bomb hedge as before, just against the new, bigger cap.

6.7 — On completion

Whenever a run reaches a terminal point — a standalone Timer finishes, or the last step of a Chain finishes, with nothing to auto-advance to — three options appear: Stop, Restart, +1 minute, applied to whichever timer just hit zero.

  • Mid-chain, between two steps, this prompt does not appear — the chain's transition mode (interaction-required / seamless) governs advancing instead.
  • Stop on a non-persistent run discards it entirely. Stop on a persistent run just ends the active session; the definition stays in the library.
  • Restart re-runs the whole thing from the top when the terminal step was the end of a chain — back to the chain's first step, not just its last leaf. For a standalone Timer (no chain involved) it just restarts that timer.
  • +1 minute extends only the terminal step in place, whether standalone or the last leaf of a chain. Neither option changes the saved definition.

09 — Making it actually fire

Permissions & reliability

  • SCHEDULE_EXACT_ALARM — required at 33+ for alarms to fire on time; requested with a plain-language rationale screen, not buried.
  • POST_NOTIFICATIONS — requested once at first alarm/timer creation.
  • Foreground service + battery-optimization exemption prompt — needed once, so a seamless timer chain survives Doze and isn't killed mid-chain.
  • Dedicated notification channels per surface (alarms, timers, chain-transitions) so the user can tune importance/sound independently in system settings.

11 — Where to go from here

Open items & next steps

  • Name: Clockr — settled.
  • Done: Room + chainlang data layer, Timers/Alarms/Stopwatch/Clock/Settings wired to real state, a first Glance clock widget. See the repo for what's actually built vs. this document's design-ahead sections.
  • Next, and the biggest remaining gap: the Timer/Chain run engine doesn't exist yet — creating and editing definitions works, but there's no foreground service, live countdown, chain-step advancement, or the §6.7 completion prompt. Nothing in §4.2's scheduled-triggers idea is buildable until this exists, since there's nothing yet to schedule into.
  • Build the completion/firing UI as one shared, pluggable module from the start — not an alarm-only screen generalized later. One controller, parameterized by which actions are valid for the context: Alarm firing gets Dismiss/Snooze; a Timer/Chain run finishing gets Stop/Restart/+1min (spec §6.7). Getting this right now avoids reconciling two divergent implementations afterward.
  • Known refactor debt once §4.2 is adopted: AlarmEntity, AlarmReceiver, and NotificationHelper as built are alarm-specific (hard-wired dismiss/snooze, oneOffAfterFire/done baked into the entity) rather than shaped around a generic scheduled-trigger + pluggable target. AlarmScheduler's actual time/repeat math, by contrast, is already target-agnostic and should carry over largely as-is.
  • Still open: exact wording/flow for the sound/transition-override UI on a Chain (picking which step to override, per chain); final default for the execution-plan-size cap; the Stopwatch-target "seed row" mechanism (§4.2).
