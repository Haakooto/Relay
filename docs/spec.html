RELAY
v1.0 · clean restart 2026-09-30 Android · Kotlin · Compose

One clock app, and timers that relay.

Relay rivals and replaces the stock Android Clock. Where the stock app is good, copy it closely. Where it is limited (timers can't chain, only alarms can be scheduled, a timer can't run twice at once), fix it.

Rev 7, a clean restart. It replaces every earlier revision and the old feature map as the design baseline. The earlier docs are still in git history. 01 · Why

Goals & principles

A one-app replacement for the stock Clock: Alarms, Timers, Stopwatch, Clock, Settings, and if feasible Bedtime, so nobody needs the stock app alongside it.

What to fix compared to the stock app

  • Timers can't chain. Relay has relays: scripted sequences of timers and other relays.
  • Only alarms can be scheduled. Relay can schedule a timer, a relay or a stopwatch as well as a plain alarm.
  • A saved timer can only run once at a time. In Relay, one definition can spawn any number of parallel runs.
  • Clock and widget styling is limited. Relay offers deep, per-instance style configuration.
  • Creating many similar alarms is tedious. A future automation API lets an on-phone assistant create them in bulk (§12).

Principles

  • An alarm must never fail to fire. Reliability beats features. Everything that rings goes through one hardened firing path (§13).
  • Separate definitions from runs. A definition is what you saved. A run is a live instance of it. One definition can have many runs.
  • One scheduling primitive. An alarm is a schedule whose target rings. Timers, relays and stopwatches are other targets on the same machinery.
  • Close copy where the stock app is good (alarm ringing screen, quick timers, world clock list). Don't reinvent what already works.
  • Fully local, no account, no sync. minSdk 33, single code path.
  • Room schema is versioned with real migrations from day one.

Non-goals

  • Sync or backup to a server.
  • Lock-screen widgets (Android removed third-party keyguard widgets).
  • Editing recorded stopwatch laps (a stopwatch is a factual record).

03 · The idea

Core model

A timer counts down. An alarm is a countdown scheduled to end at a wall-clock time. Generalizing: anything startable can be scheduled, and anything scheduled can ring.

Scheduletime + repeat + exceptions → TargetRing · Timer · Relay · Stopwatch → Runlive instance → Firingshared ring UI

Definition

  • Timer or Relay, explicitly saved to the library
  • Its label is unique and is the name relays reference
  • Idle when not running; start any time
  • Referenceable by name from any relay

Run

  • A live countdown, spawned from a definition or unsaved
  • Optional free-text label, shown on the ringing screen
  • Many runs of one definition can run in parallel
  • Own state, controls and notification
  • Persisted, so it survives a process kill and a reboot

Stopwatch

  • Counts up, with laps
  • Stays in the list until deleted, named or not

Schedule (UI: "Alarm")

  • When: time, date or repeat days, end rule, exceptions
  • What: one target (below)

Lifecycle rules

ObjectSaved (library)Unsaved (anonymous)
TimerWhen a run ends, the definition goes back to idle, ready to start againExists only as its run, optionally with a label. Gone when stopped
RelaySame as a saved timerSame as an unsaved timer
StopwatchStays until explicitly deleted, whether named or not
Schedule targetPoints at a library definitionInline, created and owned by the schedule, optionally labelled. Each fire spawns a fresh run. Save to library promotes it to a definition
Label vs. saved: any timer, relay or run can carry a free-text label ("Pasta", "Take pills"), which is shown when it rings. Saving to the library is a separate, explicit action (the Save button, not a checkbox). A saved block's label must be unique, because relays reference it by that label. Unsaved labels don't need to be unique.
04 · Pane 1

Alarms changed

A plain alarm is still two taps away. What an alarm does when it fires is a choice.

List

  • Sorted by next fire time (v0.5 sorted by hour and minute). Each row shows time, repeat summary, label, a target icon (bell / timer / relay / stopwatch) and an on/off toggle.
  • Tap a row to edit it. Create with +: the time picker comes first, as in the stock app.

Targets ("Fires")

TargetOn fireConfig
Ring (default)Full-screen ringing: Dismiss / SnoozeSound, vibration, volume ramp, snooze length, max snoozes
TimerStarts a run. Example: a countdown starting exactly at 17:00A named library timer, or an inline anonymous duration
RelayStarts a run. Example: a snooze-less wake-up of five timers with escalating soundsA named library relay, or an inline anonymous script (same editor as §05)
StopwatchCreates and starts a stopwatch at that moment. Example: counting from 16:00, lap wheneverOptional name, optional t₀

Anonymous targets don't exist beforehand: the schedule creates them. A label is optional and is shown when it rings. Save to library turns an inline target into a normal library definition, which the schedule then references.

Shared scheduling fields keep

  • Time. Either one-off (the next occurrence, or a picked date) or repeating on a set of weekdays.
  • One-off after firing: delete, or keep and disable.
  • Repeat end: never, an end date, or after N occurrences.
  • Exceptions: skip, or retime, a single date or a date range. You can apply one exception to several alarms at once (for example a vacation week).

Ringing behaviour (copy the stock app)

  • Full-screen over the lock screen and wakes the screen, with big Dismiss / Snooze controls. new
  • Rings continuously until you act on it or a ring timeout passes, and other notifications can't cut it off. new
  • Gradually increasing volume (configurable ramp) and vibration. new
  • Snooze length and max-snooze count are per alarm. When snoozes run out, Snooze is hidden. keep
  • Upcoming-alarm notification a configurable lead time before firing (stock default: 2 h), with "Dismiss now". On a repeating alarm, that adds a one-off skip exception. new
  • If it fires late (device off, clock change), it rings with a clear "delayed from 07:00" notice instead of silently skipping.
Snooze only applies to the Ring target. For Timer, Relay and Stopwatch targets, the run's own controls take over when it fires. Their "snooze" is simply the relay itself (see the wake-up example in §06).
05 · Pane 2

Timers & relays

Layout keep

  • Active runs at the top: one card per run, each with its own countdown and controls.
  • Library below: named timers and relays. Each card shows the label, the kind and the total duration, plus a ▶ start button.
  • The library can be sorted by the user, with named headers: headers move up and down, and blocks drag freely under any header.

The + menu changed

  • The existing three: New timer, New relay, New header.
  • Plus a quick-start row of four chips, default 1m 5m 10m 15m (configurable in Settings). One tap starts an anonymous timer run.

Timer

  • Fields: optional label, duration, sound (tune, vibration).
  • The config screen has Start (an unsaved run, keeping its label) and Save (to the library, requires a unique label). Saving doesn't start it. Start it from the library card.
  • Editing works on a draft: the editor opens a copy, and the definition only changes on Save. Anything started in the meantime (by hand or by a schedule) uses the saved version.
  • Parallel runs: starting "Test" while "Test" is running spawns an independent second run, labelled "Test · 2".
  • Run controls: pause/resume, reset, +1 min, stop.
  • At zero, it rings through the firing module (§13), showing its label, with Stop / Restart / +1 min. Stop on an unsaved run discards it. On a saved run, Stop just ends that run.

Relay

  • Fields: optional label, script (§06), default sound (for anonymous steps), transition mode, seamless-transition tone. keep
  • Steps can be anonymous durations, named timers, or other named relays.
  • Transition mode, per relay: seamless plays a short cue (beep, double beep, chime, pip, or silent) and continues. Interaction required rings the ending step's sound until you tap Continue (or Stop relay). keep
  • Terminal completion: Stop / Restart / +1 min. Restart goes back to the relay's first step. +1 min extends only the last step.
  • Per-step override of sound and transition mode for the boundary after a given step, so one relay can vary its own cues ("seamless into Break, but confirm before Work"). Unlisted steps keep the relay defaults. To set one, tap a step in the relay's live preview, then choose its sound and outgoing transition (provisional: confirm in the prototype). new

Script editor keep

  • Auto-closes (. new
  • Enter after ( or a separator auto-indents. new
  • Commas and newlines are both valid separators.
  • new Autocomplete: while you type a name, a drop-down lists named timers and relays that match. It leaves out the relay being edited and anything that would create a cycle.
  • Live preview: resolved steps and total duration, recomputed as you type. Errors appear inline, with position.
  • A syntax help sheet, since the language is powerful but unfamiliar to most people. That's accepted.
  • A relay can never contain itself, directly or indirectly. Saving is rejected, and the cycle path is shown (Workday → Session → Workday).
06 · The hard part

Relay language

Carried over from chainlang, with one extension: a named block can be used as a number in duration arithmetic.

relay      = "(" element (sep element)* ")"
sep        = "," | NEWLINE
element    = ref | dur_expr [STRING] | call | relay   // STRING: optional label, e.g. 5m "stretch"
ref        = IDENT                      // bare name: a reference step, keeps its identity and sound
call       = "repeat" "(" int_expr "," element ")"
           | "range" "(" num_expr "," num_expr ["," num_expr] ")"  // fractional allowed
dur_expr   = dur_term (("+" | "-") dur_term)*
dur_term   = literal | int_expr | ref_value
ref_value  = IDENT                      // inside arithmetic: that block's total duration  NEW
literal    = (NUMBER "h")? (NUMBER "m")? (NUMBER "s")?
int_expr   = int_term (("+" | "-") int_term)*    // bare number = minutes
int_term   = NUMBER | "RANDOM" "(" int_expr "," int_expr ")"
           | ("MINUTE" | "HOUR" | "SECOND") "(" "NOW" (("+"|"-") literal)? ")"
           | "(" int_expr ")"
num_expr   = int_expr with decimal NUMBERs allowed  // minutes, rounded to whole seconds

Rules

  • A bare name is a reference: (Test2) runs Test2 as a step, with its own sound. References are resolved when a run starts, so retuning Test2 updates every relay that uses it. Once started, a run is a frozen snapshot.
  • A name inside arithmetic is a value new: with Test2 = 10m, (Test2 - 2) is a relay of one anonymous 8m step. Test2 + 30s also works. A relay name used this way contributes its total duration. A result ≤ 0 is an error. Sound: with exactly one name in the expression, the step inherits that block's sound. Otherwise it uses the relay default.
  • range(a, b, step) expands to anonymous steps of a, a+step, … minutes, half-open, direction-aware (numpy semantics). Fractional values are allowed: range(1, 3, 0.5) gives 1m, 1m30s, 2m, 2m30s. arange is dropped changed. repeat(n, element) repeats any element, references included.
  • An anonymous step can carry a display-only label, written 5m "stretch", which is shown at ring time. new
  • NOW is evaluated once, when the run starts.

Worked examples

BlockDefinitionTotal
WorkTimer · 25m · sound: sadsong25m
BreakTimer · 5m · sound: happysong5m
SessionRelay · repeat(4, (Work, Break)) · seamless2h
WorkdayRelay · (Session, 30, Session, 60, Work)5h 55m
WakeRelay · (Nudge, Nudge, Louder, Loud, Siren), five 5m timers with escalating sounds · interaction required · scheduled Mon–Fri 06:3025m

Wake is the snooze-less wake-up call. Each boundary rings with the ending step's sound until you tap Continue, which starts the next five minutes. It's snooze with character, and Stop relay ends it when you're actually up.

Safety limits keep

LimitDefaultConfigurable
Reference graph is a DAG (no self-containment)alwaysNo
Max reference depth20No
Max resolved plan size, counted across all references300 stepsYes, hard ceiling 1000
Max repeat/range multiplier200No
Max expression length2000 charsNo
Long-relay warningabove 24 hYes

What each check guards against

CheckWhenCatches
Cycle check over the whole reference graphEvery save and rename of a relay or timerSelf-containment, direct (R1 → R1) or indirect (R1 → R2 → R1), with the path in the error
Shape check on one script's ASTEvery keystroke and save, before expansionNesting bombs inside one script (repeat(200, repeat(200, …))). It treats each reference as one opaque step, so on its own it does not catch cycles or big referenced blocks
Plan check on the fully expanded planRun start, and in the editor previewTotals across references (repeat(200, BigRelay)) and max depth. It also stops expanding if the depth limit is hit, so a cycle that slips past save (a bad import, say) fails safely instead of overflowing the stack new
v0.5 gap: only the first two existed. The run engine expanded referenced relays recursively without re-checking the combined size or depth, so a relay made of big referenced relays could exceed the plan cap.

12 · Hands-free

Automation & assistants later

Future feature, not in 1.0. The design is kept here so the command layer can be shaped for it from the start. Only the command layer itself (one internal API that the UI also uses) is built in 1.0.

"Five wake-up alarms, five minutes apart" shouldn't need a loop in the relay language, which would be hard to build and hard to use. An assistant can do the looping instead. Relay just needs a clean API for it.

All three entry points call one internal command layer, the same one the UI uses. So validation is identical: scripts are parsed, cycle-checked and size-checked no matter who submits them.

Entry pointWhat it coversStatus
Standard Android clock intents: ACTION_SET_ALARM, ACTION_SET_TIMER, ACTION_SHOW_ALARMS, ACTION_SHOW_TIMERS, ACTION_DISMISS_ALARM, ACTION_SNOOZE_ALARMWhat Gemini and other assistants already send to "the clock app" for "set an alarm for 7". One plain alarm or timer per intent, but an assistant can send several. A label passes through as the run labelFuture. Well-established API, the first to build
Batch import: a JSON document, received by share-to-Relay (text or .json) or a VIEW intentAny number of schedules, timers and relays, including scheduled relay targets. Works with any AI app that can produce textFuture
AppFunctions (androidx.appfunctions, Android 16+)Typed functions (createSchedules, startTimer, listAlarms, …) that on-device agents discover and call directly, with no text round-tripFuture, after a spike. Newest and least certain. First verify that Gemini actually calls third-party AppFunctions on your device

Batch format (sketch)

{
  "relay": 1,
  "schedules": [
    { "time": "06:30", "repeat": ["MO","TU","WE","TH","FR"], "label": "wake_1", "target": { "ring": {} } },
    { "time": "06:35", "repeat": ["MO","TU","WE","TH","FR"], "label": "wake_2", "target": { "ring": {} } },
    { "time": "17:00", "target": { "relay": { "ref": "Workday" } } }
  ],
  "library": [
    { "kind": "timer", "label": "Tea", "duration": "4m" },
    { "kind": "relay", "label": "Wake", "script": "(Nudge, Nudge, Loud)", "transition": "interaction" }
  ]
}

Rules

  • JSON, formatted for people too: short keys, times and durations as plain strings ("06:30", "4m"), and relay content written in the relay language. You can hand-edit it as easily as an assistant can generate it.
  • Becoming the handler: assistants send standard intents to whichever app handles them. A one-time onboarding hint explains how to make Relay that app. Verify how Gemini picks the handler when this is built.
  • A human confirms every batch: the preview shows each item, and you can untick items. Nothing is written until you tap Create.
  • Deleting or bulk-disabling through any entry point always asks for confirmation in the app. Standard intents that only create or show things need no extra step, matching stock behaviour.
  • Everything created externally gets a small "added by <app>" marker, so it's easy to find and undo.
  • One Settings switch turns all external control off.
  • The JSON schema is published in the app's help and in the repo, so any assistant can be pointed at it.
13 · Making it actually fire

Firing & reliability

Built first and tested hardest. Everything that makes noise goes through one module.

The firing module

One controller, parameterized by context. It owns the looping audio, the vibration, the full-screen activity and the notification:

ContextActions
Ring schedule firesDismiss · Snooze (hidden once max snoozes is reached)
Relay boundary, interaction requiredContinue · Stop relay
Timer / relay reaches its endStop · Restart · +1 min
  • If several things ring at once (two timers, or an alarm during a run), they stack on one ringing screen and each is dismissed on its own.
  • Audio: USAGE_ALARM, looping, with audio focus. It plays at alarm volume even when media is muted.

Scheduling

  • setAlarmClock() for Ring schedules. It's the most Doze-proof option and shows the system "next alarm" indicator.
  • Exact alarms for every run's next step end and for non-Ring schedules. UI countdowns are computed from the persisted end timestamp.
  • Reschedule everything (schedules, active runs, widget ticks) on boot, on time change, on time-zone change and on app update.

Permissions

  • USE_EXACT_ALARM. Google Play auto-grants it to apps whose core function is an alarm clock or timer, so no permission screen is needed and the user can't revoke it by accident. v0.5 used SCHEDULE_EXACT_ALARM, which the user must grant in system settings and can revoke.
  • USE_FULL_SCREEN_INTENT, gated by canUseFullScreenIntent() on API 34+, with a heads-up fallback.
  • POST_NOTIFICATIONS, requested at first alarm or timer creation. Battery-optimization exemption, prompted once.
  • Notification channels: ringing alarm, ringing timer, run progress (low), upcoming alarm, stopwatch, errors.

16 · Order of work

Build order

  1. Foundation: project skeleton, theme tokens, navigation, i18n setup, Room with a migration test harness, chainlang carried over with its tests. Fresh start, with no import from v0.5: use a new database file name, so installing over v0.5 never opens its version-5 schema. The old file is deleted on first launch.
  2. Firing module + Ring schedules: plain alarms end to end, including full-screen, looping audio, snooze, exceptions, upcoming notification and boot rescheduling. Test on the device before moving on.
  3. Run engine + Timers: persisted runs, parallel runs, quick-start, library with headers.
  4. Relays: ref arithmetic in chainlang, the script editor with autocomplete, transitions.
  5. Scheduled targets: Timer, Relay and Stopwatch on the Alarms pane.
  6. Stopwatch (persisted).
  7. Clock pane + ClockStyle renderer + widgets.
  8. After 1.0: automation (standard clock intents, then batch import, then AppFunctions after a spike), Bedtime (after a feasibility spike), extra widgets.

Worth salvaging from v0.5

  • chainlang/ in full, including its tests.
  • The AlarmScheduler next-trigger math, including exceptions. It's target-agnostic already.
  • Library header and drag-reorder logic. The analogue hand-angle geometry. The strings.xml translations (en + nb). gitVersionName().
